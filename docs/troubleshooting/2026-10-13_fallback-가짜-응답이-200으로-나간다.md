# 2026-10-13 · 모델이 죽으면 가짜 응답이 HTTP 200으로 나간다

## 증상

게이트웨이 서버를 실제 Qwen + Jev로 처음 켜서 장애 시나리오를 시험했다. 소형 모델의 키를 일부러 틀린 값으로 바꾸고 쉬운 질문을 보냈다.

- 소형 호출은 `HTTP 401`로 실패했다(trace의 `provider error`).
- 그런데 요청은 **200으로 성공**했고, 응답 본문은 다음과 같았다.

```
[fallback-mock] What is the capital of France? Answer with one word.
```

질문을 그대로 따라 말한 의미 없는 문장이다. 클라이언트는 이것을 정상 답으로 읽는다. 장애 사실은 응답의 `model` 필드(`fallback-mock`)와 DB의 trace에서만 알 수 있어서, 장애가 조용히 묻혔다. 같은 실행에서 응답에는 라우터가 어느 경로를 골랐는지도 드러나지 않는다는 것(문제 4)도 함께 확인됐다.

## 원인

1단계에서 "Jev·외부 API가 죽어도 시스템은 응답해야 한다"는 원칙을 **항상 오프라인인 mock fallback**으로 구현했다. 그 선택은 mock 환경의 테스트에서는 충분했다. 실제 모델이 붙고 나서야 두 가지가 틀렸다는 것이 보였다.

1. **"응답이 온다"와 "쓸 수 있는 답이 온다"를 같은 것으로 봤다.** mock은 질문을 따라 말할 뿐이라, 대체 응답이 정상 응답과 구분되지 않은 채 200으로 나갔다.
2. **대체 수단이 이미 있었는데 쓰지 않았다.** 소형이 죽어도 상용 모델은 살아 있고, 반대도 마찬가지다. 가짜 응답 대신 다른 경로의 실제 모델로 답할 수 있었다.

## 시도한 것

실가동 문서에 세 후보를 적고 결정을 미뤘다.

| 후보 | 판단 |
|---|---|
| (a) 응답 헤더로 fallback 사용을 알린다 | **채택**(아래 (b)와 함께). 단독으로는 가짜 응답을 200으로 내보내는 문제가 그대로 남는다 |
| (b) mock 대신 **다른 경로의 실제 모델**로 먼저 대체한다 | **채택**. 소형이 죽으면 상용, 상용이 죽으면 소형 |
| (c) 모든 실제 모델이 실패했을 때만 오류를 돌려준다 | **채택**(502). 이때도 mock으로 답하지 않는다 |

결정 근거와 주의점은 [architecture.md](../architecture.md)의 결정 기록에 남겼다. 상용 → 소형 대체는 답의 품질이 낮아질 수 있어, 헤더로 구분되게 했다.

## 해결

- `providers/registry.py`: `ProviderRegistry.failover_chain(route)`가 고른 provider → 다른 경로의 provider → (있다면) 명시적 최후 provider 순으로 돌려준다. 같은 객체는 한 번만 시도한다. `fallback`은 선택 항목이 되었다.
- `gateway/wiring.py`: 운영 wiring에서 `fallback-mock`을 제거했다.
- `gateway/pipeline.py`: 시도마다 `provider` trace 이벤트를 남기고, 대신 답한 모델의 토큰은 **그 모델 경로의 단가**로 계산한다.
- `gateway/routes.py`: 응답 헤더 `X-LLMOps-Route`, `X-LLMOps-Fallback`, `X-LLMOps-Route-Reason`, `X-LLMOps-P-Easy`. 사유는 `:` 앞 범주만, 비ASCII면 생략한다(`keyword:분석`이 헤더로 나가지 않도록).
- 테스트(`tests/test_pipeline_e2e.py`, `tests/test_routing_e2e.py`): 소형 실패 → 상용 응답과 단가, 상용 실패 → 소형 응답, 전부 실패 → 502와 시도 2건 기록, 최후 provider 사용 순서, 운영 wiring에 mock fallback이 없음, 같은 provider 중복 시도 방지, 정상 경로와 hybrid 경로의 헤더, 한글 키워드 사유.

## 배운 점

- **대체 응답은 "응답했는가"가 아니라 "쓸 수 있는가"로 판단한다.** 장애 시에도 계속 응답하는 시스템을 만들려다 장애를 숨기는 시스템을 만들었다.
- **mock 환경에서만 검증한 안전장치는 실제 환경에서 다시 본다.** 1단계 테스트는 모두 통과했다. 틀렸다는 것은 실제 모델로 서버를 한 번 켜 본 뒤에야 보였다.
- 품질이 낮아질 수 있는 대체는 허용하더라도 **응답 자체에 표시**한다. 로그에만 남기면 호출하는 쪽이 알 수 없다.
- 원칙 문구도 구현과 함께 고쳐야 한다. `CLAUDE.md`의 "mock/오픈소스 fallback을 항상 유지한다"를 "다른 경로의 실제 모델로 대체하고 mock은 개발·테스트에서만 쓴다"로 바꿨다.

## 점검한 범위와 못 한 것

- 점검: 위 자동 테스트(전부 mock provider를 장애 주입으로 사용). 코드 변경 후 전체 테스트 584개 통과.
- **점검하지 않음**: 수정 후에 실제 Qwen으로 장애 시나리오(소형 키 오류)를 다시 돌려, 상용 모델이 실제로 대신 답하는지 확인하지 않았다. 실호출은 비용이 들어 별도로 요청받을 때 한다.
- 점검하지 않음: 대체 모델의 지연 부담. 소형이 시간 초과로 실패하면 사용자는 실패 지연 + 상용 지연을 합쳐 기다린다. 시간 초과 설정과 재시도 정책은 다루지 않았다.
- 한계: 한쪽만 mock인 개발용 혼합 구성에서는 실제 모델이 실패했을 때 mock이 대신 답할 수 있다. 헤더와 `model` 필드로 드러나지만 막지는 않는다.
