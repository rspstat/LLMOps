## 2단계(라우팅 엔진 v1) 진행 기록

- **조사**: Jev 공식 문서를 못 찾아 서드파티 문서(LiteLLM, DigitalOcean)에서 `state`+`questions` 요청 형식과 `answers.<키>.choice/probabilities/confidence` 응답 형식을 확인. 공식 문서가 아니라는 점과 실호출 미검증을 코드 주석·결정 기록·README에 명시.
- **Docker 질문 답변**: 0~2단계에는 불필요, PostgreSQL·Qdrant 도입(3단계 전후)과 vLLM(WSL2/Docker 필요) 시점에 재검토 → 결정 기록에 반영.
- **구현**: `DecisionProvider`(생성용 `Provider`와 분리) → mock 판정기 → `JevProvider` → 정책(`router/policy.py`) → `HybridRouter` → 파이프라인 `judge` 이벤트 → 스모크 `--target jev`. 단계마다 pytest·ruff 통과 후 커밋 (최종 144개 테스트).
- **AI가 스스로 발견해 고친 것**:
  - 내가 쓴 테스트 하나가 `... or True`로 아무것도 검증하지 못하고 있었음 → 코루틴 함수 여부를 확인하는 실제 단언으로 교체.
  - 스모크 테스트에서 `monkeypatch.undo()`가 autouse 네트워크 차단 장치까지 해제하는 구조였음 → 테스트를 둘로 분리.
  - ruff B008(`Price()` 기본 인자) → 선택 인자 + 내부 기본값으로 수정.
- **실서버 확인**: `ROUTER_MODE=hybrid`로 uvicorn 실행 → 쉬운 요청(소형), 애매한 요청(`promoted_low_confidence`로 승격), 키워드 요청(판정기 호출 없음)을 HTTP로 확인하고 trace 행을 직접 조회.
- **하지 않은 것**: 실제 Jev/SLM/상용 API 호출(키·접근 권한 없음, 비용 규칙). mock 판정기는 요청 길이만 보므로 라우팅 품질의 근거가 아님.

## AI 응답 요약 / 채택한 내용

- **환경 점검 후 계획 수정**: docker/psql이 없고 시스템 `python`이 msys64와 3.14로 혼재함을 확인해, 처음부터 PostgreSQL을 쓰는 안의 위험을 근거로 SQLite 우선안을 추천했고 채택됨.
- **승인 없는 설치 보류**: uv가 없을 때 임의로 설치하지 않고 "설치해 줘"라는 명시적 승인을 받은 뒤 winget으로 설치.
- **작은 단위 구현**: 단계마다 `pytest` / `ruff`를 실제로 실행해 통과시킨 뒤 커밋 (총 13개 커밋). 최종 83개 테스트 통과.
- **구현 중 설계 변경**: 클라이언트 `X-Request-ID`를 trace 키로 쓰는 계획의 결함(재사용 시 저장 실패·오염)을 발견해 서버 생성 ID로 변경 → `docs/troubleshooting/2026-10-13_request-id-충돌.md`.
- **실서버 확인**: TestClient 외에 uvicorn으로 실제 HTTP 요청 → 200 / 400 응답과 SQLite 저장 행을 직접 확인.
- **실호출은 하지 않음**: `.env`와 키가 없어 스모크를 실행할 수 없었고, 비용 규칙(요청 시에만 실호출)에 따라 시도하지 않음. `openai_compat`은 mock HTTP로만 검증됨.
- **버린 것**: 처음 계획한 `TRACE_DB_PATH` 변수(→ `DATABASE_URL` 하나로 통일), setuptools 패키징(→ `package = false`), 잘못 쓴 `anyio_mode` pytest 옵션(실행 전에 발견해 제거).

## 확인이 필요한 것

- 실제 SLM·상용 API·Jev로 한 번씩 스모크 호출 (`ALLOW_LIVE_CALLS=1`, `.env` 설정 필요). Jev 어댑터는 이때 처음 실제 검증된다
- Jev 접근 권한(공식 대기자 명단, Vercel AI Gateway, DigitalOcean) 승인 여부
- Starlette의 `httpx2` deprecation 경고 대응 여부
