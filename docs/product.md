# 제품 정의: LLMOps 게이트웨이

> 이 문서는 서비스가 **무엇을 제공하는지**를 자연어로 정의합니다. 상태 표기는 2026-10-13 기준이며 자동 테스트 577개와 첫 실측(Qwen + Jev, 80문항)으로 확인한 것만 "구현됨"으로 적었습니다. 설계 근거와 결정은 [architecture.md](architecture.md), 실측 결과는 [evals/2026-10-13_qwen-first-run.md](evals/2026-10-13_qwen-first-run.md)에 있습니다.

## 1. 한 줄 요약

LLM을 쓰는 앱이 OpenAI 대신 호출하는 **중간 서버(LLM 게이트웨이)** 입니다. 요청을 받으면 입력을 검사하고, 쉬운 요청은 값싼 소형 모델로, 어려운 요청은 상용 모델로 보내고, 모든 과정을 기록하며, 설정을 바꿀 때마다 비용·지연·정확도를 측정할 수 있게 합니다.

사용자에게 보이는 화면이 있는 서비스가 아니라 **HTTP API**입니다. 사용자는 챗봇 같은 LLM 기능을 만드는 개발자이고, 그 앱의 최종 사용자는 이 서버의 존재를 알 필요가 없습니다.

```
앱 ──요청──▶ 입력 가드 ──▶ 라우터 ──▶ 모델 호출 ──▶ 응답
                │            │          │
                └────────────┴──────────┴──▶ trace 기록 (판정·모델·토큰·비용·지연)
```

## 2. 누가, 왜 쓰는가

| 문제 | 지금 흔한 방식 | 이 서비스 |
|---|---|---|
| 비용 | 모든 요청을 가장 좋은(비싼) 모델로 보냄 | 요청의 난이도를 판정해 **쉬운 요청은 소형 모델**로 보냄 |
| 안전 | 입력 검증을 앱마다 따로 구현 | 호출 전에 **게이트웨이에서 한 번에 차단** |
| 투명성 | 어떤 모델이 왜 답했는지, 얼마 들었는지 모름 | 요청마다 **ID와 단계별 기록** |
| 개선 | 설정을 바꿔도 나아졌는지 모름 | **평가 도구**가 설정별 비용·지연·정확도를 측정 |
| 장애 | 모델 서버가 죽으면 앱도 실패 | 모델 호출이 실패해도 **오프라인 fallback으로 응답** |

## 3. 요청 하나가 겪는 일

`POST /v1/chat/completions` (OpenAI 호환 형식, Bearer 인증, 비스트리밍)

1. **요청 ID 발급**: 서버가 항상 새 ID를 만들어 응답 헤더 `X-Request-ID`로 돌려줍니다.
2. **입력 가드**: 빈 입력, 길이 초과, 명백한 프롬프트 인젝션이면 **400**으로 거절합니다. 응답에는 범주만 알려 주고 어떤 규칙에 걸렸는지는 기록에만 남깁니다.
3. **라우팅**: 소형 모델과 상용 모델 중 하나를 고릅니다(아래 FR-4).
4. **모델 호출**: 고른 모델을 호출합니다. 실패하면 오프라인 fallback으로 한 번 더 시도하고, 둘 다 실패하면 **502**를 돌려줍니다.
5. **기록**: 단계마다 판정·모델·토큰·비용·지연을 trace로 저장합니다. 저장이 실패해도 응답은 정상으로 돌려줍니다.
6. **응답**: OpenAI 응답 형식으로 돌려줍니다. `model` 필드에 실제로 답한 모델 이름이 들어갑니다.

요청 예시:

```json
POST /v1/chat/completions   (Authorization: Bearer <게이트웨이 키>)
{"messages": [{"role": "user", "content": "프랑스의 수도는? 한 단어로 답하세요."}],
 "max_tokens": 64}
```

응답 헤더 `X-Request-ID: <32자 ID>`, 본문은 `choices[0].message.content`, `model`, `usage`를 담습니다. 인젝션 문구가 포함되면 `400 {"error": {"code": "input_blocked", ...}}`입니다.

## 4. 기능 요구사항

상태: **구현됨**(코드와 테스트로 확인), **부분**(일부만), **예정**(로드맵에 있고 아직 없음).

| ID | 요구사항 | 상태 | 비고 |
|---|---|---|---|
| FR-1 | 시스템은 OpenAI 호환 `chat/completions` 요청(메시지, `max_tokens`, `temperature`)을 받아 같은 형식으로 응답해야 한다. 기존 OpenAI 클라이언트의 주소만 바꿔 쓸 수 있어야 한다 | 부분 | OpenAI 요청의 **일부만** 지원한다(문자열 메시지, `max_tokens`, `temperature`). 도구 호출, 이미지, 스트리밍(400)은 미지원. `model` 필드는 받지만 라우터가 결정한다 |
| FR-2 | 시스템은 Bearer 키가 없거나 틀린 요청을 401로 거절해야 한다. 서버에 키가 설정되지 않았으면 모든 보호된 요청을 거절해야 한다 | 구현됨 | 사용자별 키·한도는 예정. 401과 422의 오류 본문이 OpenAI 형식(`error`)이 아니라 FastAPI 기본 형식(`detail`)이다 |
| FR-3 | 시스템은 모델을 호출하기 전에 빈 입력, 길이 초과(기본 8000자), 영어·한국어의 명백한 인젝션 문구를 차단해야 한다. 차단 사유의 세부 규칙은 응답에 노출하지 않는다 | 구현됨 | 정규식 수준이다. 분류기·PII 탐지·공격 프롬프트 자동 생성은 4단계 예정 |
| FR-4 | 시스템은 요청마다 소형·상용 중 하나를 골라야 한다. 모드는 설정으로 고른다: `rules`(길이·키워드 규칙만), `hybrid`(규칙에 걸리면 확정, 아니면 판정기), `judge_only`(항상 판정기) | 구현됨 | 기본은 `rules`. 판정기 확률이 임계값 미만이면 상용으로 승격한다 |
| FR-5 | 시스템은 판정기(Jev)에게 "쉬움/어려움"과 확률을 묻고, `p(easy)`가 임계값 이상일 때만 소형 모델로 보내야 한다. 판정기가 실패하면 규칙 결과로 대체하고 그 사실을 기록해야 한다 | 구현됨 | 실제 Jev API로 확인했다. 정책 v1은 80문항 전부 easy로 판정해 개선이 필요하다 |
| FR-6 | 시스템은 모델 호출이 실패하면 오프라인 fallback으로 응답하고, 둘 다 실패하면 502를 돌려줘야 한다. fallback으로 답했다는 사실은 응답의 `model`과 기록에 드러나야 한다 | 부분 | 동작은 실제 모델로 확인했으나, fallback 응답이 **질문을 따라 말하는 의미 없는 문장이고 HTTP 200**으로 나가 장애가 묻힌다([발견한 문제](evals/2026-10-13_gateway-live-run.md)). 다른 경로의 실제 모델로 먼저 대체하거나 헤더로 알리는 개선이 필요하다 |
| FR-7 | 시스템은 요청마다 서버가 만든 ID를 응답 헤더로 돌려주고, 단계(가드·판정·라우팅·모델 호출)별로 판정, 확률, 모델, 토큰, 비용, 지연을 기록해야 한다 | 구현됨 | SQLite. 클라이언트가 보낸 ID는 안전할 때만 상관관계용으로 함께 기록한다 |
| FR-8 | 시스템은 모든 임계값(입력 길이, 긴 프롬프트 기준, 키워드, 승격 임계값, 단가)을 코드가 아니라 설정으로 바꿀 수 있어야 한다 | 구현됨 | 평가 도구가 값을 바꿔 가며 측정하기 위함 |
| FR-9 | 시스템은 프롬프트 본문을 기본으로 저장하지 않고(길이와 해시만), 설정 오류 메시지·점검 출력·리포트에 API 키와 계정 ID를 노출하지 않아야 한다 | 구현됨 | 이 범위는 테스트로 확인했다. 본문 저장은 옵션. 키 노출 버그를 테스트로 발견·수정했다([기록](troubleshooting/2026-10-13_설정-오류에-키-노출.md)) |
| FR-10 | 시스템은 데이터셋으로 소형·상용·판정기를 한 번씩 호출해 캐시하고, 캐시를 재생해 설정별(모드, 임계값) 정확도·비용·지연과 판정기 품질을 비교하는 리포트를 만들어야 한다 | 구현됨 | `evals/`. 임계값을 바꿔도 추가 호출이 없다 |
| FR-11 | 시스템은 비용이 드는 호출을 명시적으로 켠 경우에만 실행하고, 예산 상한과 단가 설정이 없으면 거부해야 한다 | 부분 | **평가 도구** 기준으로 구현됨(`ALLOW_LIVE_CALLS=1`과 `--budget-usd` 필수). 게이트웨이 서버는 모델 스위치를 켜는 것으로만 제어되고 실요청에 예산 상한이 없다 |
| FR-12 | 시스템은 설정(`.env`)이 실제로 무엇을 켜는지, 키가 채워졌는데 스위치가 꺼져 있는지, 주소·단가가 틀렸는지를 비밀 값을 보여 주지 않고 알려 줘야 한다 | 구현됨 | `evals.run check` |
| FR-13 | 시스템은 모델의 응답이 완성되기 전에 조각으로 흘려보내는 **스트리밍**을 지원해야 한다 | 예정 | 현재 400 |
| FR-14 | 시스템은 모델의 **응답**도 검사(출력 가드)해야 한다 | 예정 | 현재는 입력만 |
| FR-15 | 시스템은 사용자가 요청과 판정을 눈으로 확인할 **시연 화면/대시보드**를 제공해야 한다 | 예정 | 7단계. `demo_app/`은 비어 있다 |
| FR-16 | 시스템은 가드와 라우팅 분류기를 파인튜닝한 소형 모델로 대체·비교(Jev 대 분류기 대 LLM judge)할 수 있어야 한다 | 예정 | 5~6단계 |
| FR-17 | 시스템은 사용자별 키, 요청 한도, PostgreSQL 저장소를 지원해야 한다 | 예정 | 필요해질 때 도입 |

## 5. 비기능 요구사항

- **안전한 기본값**: 아무 설정을 하지 않으면 모든 모델이 오프라인 mock이라 외부 호출과 비용이 없다.
- **비용 통제**: 과금되는 모델은 단가와 예산 없이 호출하지 못한다.
- **재현성**: 평가 캐시는 프롬프트, 모델, 엔드포인트, 정책 버전, 추가 요청 필드가 하나라도 바뀌면 다시 수집한다. 서로 다른 설정의 결과를 한 리포트에 섞지 않는다.
- **정직한 표시**: 리포트는 mock, 라벨 미검토, 표본 부족, 빈 응답을 상단에 경고한다.
- **교체 가능성**: 모든 모델 호출은 공통 인터페이스 뒤에 있어서 제공사를 바꿔도 코드가 바뀌지 않는다(설정으로 전환).
- **장애 내성**: 판정기나 모델이 장애여도 시스템은 응답한다(기록에 사유가 남는다).

## 6. 현재 범위 밖

- 모델 호스팅·파인튜닝 서비스 제공(파인튜닝은 5단계에서 소형 모델 실험으로만 다룸)
- 사람이 쓰는 챗 UI 제품(시연용 화면만 예정)
- 긴 생성·요약·창작 같은 정답이 없는 요청의 품질 평가(규칙 채점이 가능한 짧은 정답형만 측정)
- 다중 테넌트, 과금, 감사 로그

## 7. 성공 기준

| 지표 | 정의 | 현재 값 (첫 실측, n=80) |
|---|---|---|
| 정확도 | 규칙 채점이 가능한 문항의 정답률 | 소형 91.2%, 상용 97.5% |
| 비용 | 1천 요청당 비용, 상용 단독 대비 절감률 | 소형 단독 98% 절감. 판정기 사용 시 임계값 0.995에서 정확도 97.5% 유지, 47% 절감 |
| 지연 | p50 / p95 | 소형 658 / 828 ms, 상용 1031 / 1610 ms, 판정 호출 약 +200 ms |
| 라우팅 품질 | 판정기의 `p(easy)`가 "소형이 틀릴 문항"을 가려내는가 | AUC 0.935 (틀린 문항 7개 기준) |
| 방어율 | 인젝션·PII 공격 중 차단된 비율 | 아직 측정하지 않음 (4단계) |

**읽을 때 주의**: 표본이 80개이고 난이도 라벨이 검토 전이며, 임계값 0.995는 같은 데이터를 본 뒤에 골랐기 때문에 **낙관적인 수치**입니다. 보류 데이터와 더 큰 표본으로 확인해야 합니다.

## 8. 차별점과 그 검증 상태

LLM 게이트웨이와 모델 라우터 자체는 이미 있는 종류의 서비스입니다(이 프로젝트에서 기존 서비스를 조사하지는 않았습니다). 차별점은 다음 세 가지이고, 검증된 정도가 서로 다릅니다.

| 주장 | 검증 상태 |
|---|---|
| **판정 전용 모델(Jev)로 라우팅**한다. 글을 쓰는 LLM이 아니라 선택지와 확률을 돌려주는 모델이라 빠르고 싸다 | 일부 확인: 실제 API로 동작하고 순위 신호가 있음. 단 정책 v1은 `hard`를 한 번도 내지 않았고 속도·비용 수치는 회사 발표값(비용은 실측으로 입력 약 490토큰/호출 확인) |
| **평가가 라우팅 정책을 개선하는 폐쇄 루프**. 설정마다 비용·지연·정확도·방어율을 측정하고 그 결과로 정책을 고친다 | 부분: 측정 도구는 있고, 결과를 보고 정책을 고치는 과정은 사람이 하는 중(정책 v2 예정) |
| **한국어 요청 대상의 가드와 평가** | 약함: 데이터셋 40문항이 한국어이고 가드에 한국어 규칙이 있는 수준. 고도화는 4단계 |

## 9. 시연 시나리오 (계획)

1. 쉬운 질문 → 소형 모델이 답하고 기록에 판정 확률이 남는다.
2. 어려운 질문 → 상용 모델로 승격되고 비용 차이가 보인다.
3. 인젝션 문구 → 400으로 차단되고 호출은 일어나지 않는다.
4. 모델 장애를 흉내 낸 요청 → fallback으로 응답하고 사유가 기록된다.
5. 평가 리포트 → 설정(임계값)에 따른 정확도·비용 곡선을 보여 준다.

1~4는 2026-10-13에 서버를 실제 Qwen·Jev로 켜서 확인했습니다([상세](evals/2026-10-13_gateway-live-run.md)). 화면 없이 터미널과 리포트로 시연할 수 있고, 최소 시연 화면이 다음 작업입니다. 4번(장애 시 fallback)은 동작하지만 응답이 의미 없는 echo로 HTTP 200으로 나가는 문제가 확인되어 개선이 필요합니다.

## 10. 제약과 가정

- 대회 일정: 중간 발표 11/5(예정, 5~7분), 최종 발표 12월 말(7~10분). 평가는 중간 발표에서 AI 활용 계획 40%, 최종에서 프롬프팅·트러블슈팅 40%와 작동하는 프로토타입 30%입니다([명세](contest/대회-명세.pdf)).
- Jev는 접근 권한이 있어야 쓸 수 있고 단가·속도는 회사 발표값입니다. 접근이 없으면 오프라인 mock과 규칙으로 동작합니다.
- 비용이 드는 호출은 사용자가 요청할 때만 합니다. 지금까지 전체 실측에 쓴 금액은 약 $0.01입니다.
- 파인튜닝은 GPU 제약(RTX 2070, VRAM 8GB)으로 1B 이하 모델 위주로 설계합니다.

## 11. 용어

| 용어 | 뜻 |
|---|---|
| 게이트웨이 | 앱과 LLM 사이에 놓이는 중간 서버 |
| 라우팅 | 요청을 어떤 모델에 보낼지 정하는 일 |
| 소형 / 상용 모델 | 값싸고 빠른 모델 / 비싸고 강한 모델 |
| 판정기 (Jev) | 글을 쓰지 않고 선택지(쉬움/어려움)와 확률만 돌려주는 모델 |
| 승격 | 소형으로 충분하다는 확신이 부족해 상용으로 올려 보내는 것 |
| 입력 가드 | 모델을 호출하기 전에 위험한 입력을 막는 검사 |
| trace | 요청 한 건이 거친 단계별 판정·모델·비용·지연의 기록 |
| fallback | 모델 호출이 실패했을 때 대신 응답하는 오프라인 대체 |
| 임계값 (τ) | `p(easy)`가 이 값 이상일 때만 소형 모델을 쓰는 기준 |
